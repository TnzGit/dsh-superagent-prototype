## 5. Newly identified issues to hand back to remote (minimal repros, no local patches made)

1. **Single-file apply lock error path leaks the private journal path.** `applyOneNonGitFile` → `underLock` → `open(lock,'wx')` throws the raw `EEXIST` (Node error message contains the full absolute lock path). The batch-audit path already sanitizes this (C6B2B3). Repro: create `.single-file-apply.lock` inside an owner-only journal root, then call apply; observe the thrown message embeds the private path. Expected fix: sanitize like the audit lock ("lock exists; human reconciliation required"), and never auto-delete/steal. Location: `src/local-first/non-git-apply.ts` `underLock` (~lines 105–110).
2. **Approval file is never consumed.** A still-valid (unexpired) approval file can be re-read by another process with a *different* transaction id within the expiry window; only the journal's `tx-<transactionId>` collision blocks re-use of the **same** transaction. For production one-shot semantics, remote should consume/rotate the out-of-band approval (authenticated store) rather than rely on tx-id collision alone. Location: `readApproval`/`recheckApproval` (~lines 49–77).
3. **Metadata gates (#5–#7) are design fail-closed triggers that the current single-file implementation does not enforce** (mode-masked 0o777; no ACL/xattr/special-bit capture). This is a documented design gap, not a bug to patch blind — remote should decide whether to add capture+verify or refusal, plus Mac-compatible tests.
4. Headless-CLI dispatch remains unproven on this host (missing provider credential; we did not add credentials or change defaults) — unchanged gate, recorded for honesty.
